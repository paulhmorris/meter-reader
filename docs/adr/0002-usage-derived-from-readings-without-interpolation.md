# Usage is derived from stored readings, never interpolated

Consumption is normalised to gallons at ingest (the R900 counter's last digit is tenths, so raw/10) and stored per Reading; Usage for a period is the last Reading in it minus the last Reading before it starts, bucketed in America/Chicago from UTC timestamps so DST is handled at query time. Readings arrive irregularly and the dongle can be down, so a period whose boundary Readings are too far apart is marked Partial rather than filled in — an invented number shown to a neighbour as fact is worse than an honest gap. Too far apart is 20 minutes for hourly periods — a Heartbeat interval plus slack, since a Heartbeat is forced once 15 minutes have elapsed and so lands a transmission or two late — and an hour for daily ones, following what pruning leaves behind (ADR-0003); the tolerances live once in `STALE_AFTER_MS` in `apps/web/src/lib/server/usage.ts`. Partial Usage is still shown, marked as Partial, never hidden.

A Reading whose Consumption is lower than the last stored one for that Meter is never stored, since Consumption only decreases when the counter wraps, the meter is swapped, or the packet is corrupt. How far it fell decides whether a human hears about it. A weak signal flips the counter's low digits, so a fall within `JITTER_TOLERANCE_TENTHS` in `services/ingest/src/record.ts` — a gallon, ten times the tenth-digit flip actually seen — is dropped as decode noise and only logged. A larger fall is reported to Sentry, and a wrap or a swap clears that line by orders of magnitude. The tolerance exists because an idle meter flapping its tenths digit re-reports on every transmission: the low Reading is never stored, so the stored one it is judged against never moves, and one bit of noise becomes an unbounded alert stream. No upper bound is enforced: a genuinely large jump is indistinguishable from a filled pool.
